# Notification channels (#1735)

InverseArena notifications are delivered through a common channel contract so
time-critical round alerts, payouts, eliminations, rematches and community
arena announcements can reach players where they already are. Web Push (#1571)
remains supported and is now one adapter among four.

## Architecture

```text
RoundService / RematchService / host announcement route
  -> NotificationPipelineService
       -> preference check (legacy booleans + per-event/per-channel overlay)
       -> dedupe + delivery ledger row
       -> NotificationChannel adapter
            -> PushChannel      -> PushService (VAPID / RFC 8291)
            -> TelegramChannel  -> Telegram Bot API
            -> DiscordChannel   -> Discord API user DMs
            -> WebhookChannel   -> host-configured community webhook
       -> retry with exponential backoff / dead-letter
```

The contract lives in `backend/src/services/notificationChannel.ts`. Adapters
return one of:

| Result | Meaning | Pipeline action |
| --- | --- | --- |
| `delivered` | Platform accepted the message | Mark delivery `sent` |
| `retryable` | Transient error / rate limit | Queue `retrying` with backoff |
| `failed` | Permanent error (bad link, removed webhook) | Dead-letter immediately |
| `skipped` | No destination or channel unconfigured | Remove the placeholder ledger row |

The pipeline owns preference checks, dedupe, ledger writes, retries and
dead-lettering. Adapters only translate platform responses.

## Bot account linking

One-time codes are generated by the authenticated wallet:

```text
POST /api/users/me/notification-links/telegram/code
POST /api/users/me/notification-links/discord/code
```

The response contains the code (shown once), its expiry and the exact bot
command. Codes:

- expire after 10 minutes;
- are stored only as an HMAC-SHA256 digest using `JWT_SECRET`;
- can be redeemed once (`usedAt` is set before the link is written);
- bind the platform destination to the code owner — the bot cannot link an
  arbitrary wallet.

Telegram linking uses `/start CODE`. Discord linking uses the `/link CODE`
slash command (in a DM or a server where the bot is installed). Only the chat
or user id is stored; bot tokens stay in the environment.

Inbound callbacks:

| Route | Authentication |
| --- | --- |
| `POST /api/notifications/telegram` | `x-telegram-bot-api-secret-token` compared in constant time |
| `POST /api/notifications/discord` | Ed25519 signature over `timestamp + rawBody`, max 5 minutes old |

When a bot is blocked or removed, the link is deactivated automatically so
delivery stops instead of retrying forever.

## Preferences

`GET/PUT /api/users/me/notification-channels` returns and updates:

- the legacy switches (`pushEnabled`, `roundNotifications`, …), now extended
  with `telegramEnabled`, `discordEnabled` and
  `arenaAnnouncementNotifications`;
- `channelPreferences`, an overlay of `{ eventType, channel, enabled }` rows;
- `links`, the active bot destinations.

An explicit overlay row wins. When no row exists, delivery falls back to the
legacy channel + event switches, so existing accounts keep their behaviour.

## Delivery records, retries and dead-lettering

`notification_deliveries` is the delivery ledger. New fields record:

- `attempts`, `nextAttemptAt`, `lastError`;
- `deadLetteredAt` for terminal failures;
- `context` (arena id and message) so a queued retry can be replayed without
  the caller repeating the event.

Retryable failures use `base * 2^(attempts-1)` with a default 60-second base,
a one-hour cap and five attempts by default. Platform `retry_after` values are
honoured when supplied. After the budget is exhausted the row becomes
`dead_letter`.

Run due retries from an authenticated admin cron:

```text
POST /api/notifications/retries/run?limit=100
```

## Community webhooks for hosts

Arena hosts (the wallet in `arena.metadata.createdBy`) can manage one or more
HTTPS webhooks:

```text
POST   /api/arenas/:arenaId/notification-webhooks
GET    /api/arenas/:arenaId/notification-webhooks
DELETE /api/arenas/:arenaId/notification-webhooks/:webhookId
POST   /api/arenas/:arenaId/announcements
```

Webhook URLs carry bearer-like authority, so they are AES-256-GCM encrypted at
rest with `PUSH_ENCRYPTION_KEY` and only ever returned masked. Announcements
fan out to all active webhooks for the arena in a single webhook delivery,
not once per player. 4xx responses deactivate that webhook; 429 and 5xx are
retryable.

The frontend exposes these flows in the notifications feature:

- `NotificationChannelSettings` — preference matrix and Telegram/Discord links,
  mounted under Profile → Preferences;
- `CommunityWebhookSettings` — host webhook list, add/remove and announce,
  mounted per arena in the Creator Operations Console;
- `useNotificationChannels` / `useCommunityWebhooks` — authenticated API hooks.

## Configuration

Add to the backend environment (see `backend/.env.example`):

| Variable | Purpose |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Bot API token; Telegram delivery is disabled when unset |
| `TELEGRAM_WEBHOOK_SECRET` | Shared secret for Telegram updates |
| `DISCORD_BOT_TOKEN` | Bot token for user DMs; Discord delivery is disabled when unset |
| `DISCORD_PUBLIC_KEY` | Application public key used to verify interactions |
| `NOTIFICATION_RETRY_MAX_ATTEMPTS` | Attempts before dead-lettering (default `5`) |
| `NOTIFICATION_RETRY_BASE_MS` | Base backoff in milliseconds (default `60000`) |

All are declared in `backend/src/config/env.ts`; no source file reads
`process.env` directly. Delivery is best-effort: a missing or unreachable
channel never fails round resolution, rematch creation or persistence.
